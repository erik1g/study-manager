# Releases und Versionen

Der Study Manager folgt **Semantic Versioning** (`MAJOR.MINOR.PATCH`). Versionen, Changelog und Docker-Images entstehen automatisch aus den [Conventional Commits](/entwickler/mitmachen).

## Der Ablauf

Releases werden **geplant**: Alles, was in die nächste Version gehört, sammelt sich in einem **Release-Branch**. Erst wenn er getestet ist, kommt er nach `main` und wird veröffentlicht.

```
Pull Request (Titel: feat: …)  ──squash──►  release/0.2      (CI und E2E im Pull Request)
                                               │  Images "release-0.2" zum Ausprobieren
                                               │  vorher: main in release/0.2 mergen
                                               ▼
                         Pull Request release/0.2 → main  (CI und E2E, Merge-Commit, kein Squash)
                                               │
                          release-please sammelt die Commits
                                               ▼
                       Release-PR "chore: release 0.2.0"  (Version + CHANGELOG.md)
                                               │  du mergst ihn
                                               ▼
                  Git-Tag v0.2.0  +  GitHub-Release mit Changelog
                                               │  Freigabe in der Umgebung release
                                               ▼
              Docker Hub: study-manager-server und study-manager-web
              mit den Tags 0.2.0, 0.2, 0 und latest (amd64 und arm64)
```

### Regeln

- Es gibt **immer nur einen** Release-Branch, benannt nach der geplanten Minor-Version: `release/0.2`. Er wird von `main` abgezweigt, wenn das vorige Release fertig ist.
- **Features und alles andere** gehen per Pull Request (Squash) in den Release-Branch. Der **Titel** folgt Conventional Commits und wird zum Commit-Titel. Pull Requests in einen Release-Branch und aus ihm heraus durchlaufen **immer** die E2E-Tests (ohne Label); direkt auf den Branch wird nichts gepusht.
- **Hotfixes** (`fix:` für die veröffentlichte Version) und Sicherheitsthemen gehen direkt per Pull Request nach `main` und geben einen Patch-Release (`0.1.1`). Danach wird `main` in den Release-Branch gemergt.
- **Release-Branch → `main`** immer als **Merge-Commit**, nie als Squash: Nur so bleibt jedes `feat:` und `fix:` ein eigener Eintrag im Changelog, und die Version wird aus allen Commits berechnet.
- Der Name des Branches ist ein Plan. Die Version berechnet release-please aus den Commits; soll sie anders lauten, steht `Release-As: 0.2.0` im Text eines Commits.

### Ein Release, Schritt für Schritt (Maintainer)

```sh
# 1. Anfangen (nach dem vorigen Release)
git fetch origin && git switch -c release/0.2 origin/main && git push -u origin release/0.2

# 2. Sammeln: Pull Requests gegen release/0.2 prüfen und mit Squash mergen.
#    Ausprobieren mit den Images study-manager-server:release-0.2 und study-manager-web:release-0.2.

# 3. Abschließen: erst main hereinholen (Hotfixes), dann nach main – beides als Merge-Commit,
#    weil der Release-Branch geschützt ist und nur Pull Requests annimmt.
gh pr create --base release/0.2 --head main --title "chore: merge main into release/0.2"
gh pr merge <nummer> --merge
gh pr create --base main --head release/0.2 --title "chore: merge release/0.2 into main"
gh pr merge <nummer> --merge          # nie --squash

# 4. Veröffentlichen: den Release-PR von release-please mergen und in der Umgebung release freigeben.
```

Solange die Version unter **1.0** liegt, erhöht ein Bruch die Minor-Version (`0.2.0` → `0.3.0`). Ab 1.0 erhöht er die Major-Version.

## Die Images

| Image | Inhalt |
|---|---|
| `docker.io/erik1g/study-manager-server` | API, MCP-Server und Jobs |
| `docker.io/erik1g/study-manager-web` | Caddy mit der gebauten Web-App |

Tags je Release: `X.Y.Z`, `X.Y`, `X` und `latest`. Auf `main` entstehen zusätzlich `edge`, auf einem Release-Branch `release-0.2` (für `release/0.2`), auf beiden `sha-<commit>`. Diese Testimages sind **nicht signiert** und nie `latest`. Beide Images gibt es für `linux/amd64` und `linux/arm64` (zum Beispiel für einen Raspberry Pi).

## Wer ein Release auslösen darf

Ein Release soll **niemand außer den Maintainern** auslösen können. Dafür greifen mehrere Schichten ineinander:

1. **`main` und die Release-Branches sind geschützt** (Rulesets): nur Pull Requests, die Prüfungen „Typen, Tests, Build“ und „Titel folgt Conventional Commits“ müssen grün sein, keine Force-Pushes, kein Löschen. Freigeben darf nur, wer in `CODEOWNERS` steht. Beiträge von außen kommen über Forks ohne Schreibrecht, und ihre Workflows laufen ohne Zugriff auf Geheimnisse.
2. **Tags `v*` sind geschützt** (Tag-Ruleset): Nur Maintainer und der Release-Bot legen sie an oder ändern sie.
3. **Das Veröffentlichen wartet auf eine Freigabe**: Der Job, der die Images bei Docker Hub veröffentlicht, läuft in der GitHub-Umgebung `release`. Sie hat Pflicht-Prüfer und ist auf `main` beschränkt. Auch wer den Release-PR mergt, veröffentlicht damit noch nichts, bis ein Maintainer in GitHub **Approve** klickt.
4. **Die Workflows sind gehärtet**: alle fremden Actions sind auf Commit-Hashes festgelegt (Aktualisiert wird von Hand, vor einem Release), jeder Job hat nur die nötigen Rechte, `zizmor` prüft die Workflows in der CI, und die Veröffentlichung läuft nur im Original-Repository, nie in einem Fork.
5. **Die Images sind signiert** (cosign, ohne eigenen Schlüssel) und haben eine Herkunftsbestätigung; Betreiber prüfen sie mit [`cosign verify`](/admin/sicherheit).

## Einmalig einrichten (Maintainer)

- **Secrets** (*Settings → Secrets and variables → Actions*): `DOCKERHUB_USERNAME` und `DOCKERHUB_TOKEN` (ein Zugriffstoken mit Schreibrecht).
- **Actions** (*Settings → Actions → General*): Workflows dürfen Pull Requests anlegen (für den Release-PR); Pull Requests von allen Externen brauchen eine Freigabe; Standard-Rechte nur lesen.
- **Umgebung `release`** (*Settings → Environments*): Pflicht-Prüfer = die Maintainer; Zweige: nur `main`.
- **Umgebung `edge`** (*Settings → Environments*): Zweige `main` und `release/*` (für die Testimages).
- **Rulesets** (*Settings → Rules*): `main` (Pull Request, Prüfungen, Code-Owner-Freigabe, keine Force-Pushes, Merge-Methoden **Squash und Merge-Commit**), `release/**` (Pull Request, Prüfungen, keine Force-Pushes, Merge-Methoden Squash und Merge-Commit; Löschen nur durch Maintainer, nach dem Release) und die Tags `v*` (nur Maintainer und der Bot `github-actions`). Maintainer dürfen eine Ausnahme per Pull Request haben, sonst könnten sie ihre eigenen Pull Requests nicht freigeben.
- **Pages**: *Settings → Pages → Source: GitHub Actions* (für diese Doku).
- **Sicherheit**: private Sicherheitsmeldungen und Push-Schutz für Geheimnisse einschalten.

Der Release-PR wird vom Bot angelegt; dessen Pull Requests lösen die Prüfungen nicht von selbst aus. Der Maintainer mergt ihn mit seiner Ausnahme für Maintainer.

## Eine Version zurückziehen

Ein fehlerhaftes Release behebst du mit einem `fix:` und einem neuen Release. Den Tag oder das Image löschst du nur im äußersten Notfall; Betreiber, die schon aktualisiert haben, brauchen ein Folge-Release.
