# Sicherheit

Der Study Manager verwaltet Konten, Dokumente und Notizen. Diese Empfehlungen halten das Risiko klein.

## Grundlagen

- **Nur HTTPS** nach außen; HTTP-Zugriffe leitest du am Proxy auf HTTPS um.
- **Port 8080 nicht ins Internet stellen.** `BIND_ADDRESS=127.0.0.1` (Standard) lässt nur den Server selbst zu; läuft dein Proxy anderswo, begrenze den Zugriff per Firewall auf ihn.
- **Updates einspielen**: den Study Manager ([Betrieb](/admin/betrieb)) und das Betriebssystem. Automatische Sicherheitsupdates (`unattended-upgrades` unter Debian/Ubuntu) sind sinnvoll.
- **SSH nur mit Schlüsseln**, am besten nur aus deinem Netz oder per VPN.
- **`.env` schützen** (`chmod 600`), nie in ein Repository legen, und `BACKUP_PASSPHRASE` getrennt aufbewahren.

## Anmeldung

- Es gibt **keine offene Registrierung**; Konten entstehen nur durch Einladungen.
- **Admins** brauchen einen Passkey oder eine Authenticator-App (zweiter Faktor).
- Die App begrenzt Anfragen pro Besucher (Rate Limits) und sperrt Anfragen an interne Adressen, wenn Nutzer Kalender-Links eintragen (Schutz vor Server-Side Request Forgery).

## Die Images prüfen

Jedes **Release-Image** wird bei der Veröffentlichung mit [cosign](https://docs.sigstore.dev/cosign/) signiert und bekommt eine Herkunftsbestätigung von GitHub (*Attestation*). So kannst du prüfen, dass ein Image wirklich aus dem Release-Workflow dieses Projekts stammt und niemand es nachträglich ausgetauscht hat:

```sh
cosign verify docker.io/erik1g/study-manager-server:0.1.0 \
  --certificate-identity-regexp 'https://github.com/erik1g/study-manager/\.github/workflows/release\.yml@.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Dasselbe gilt für `study-manager-web`. Ersetze `0.1.0` durch deine Version. Die Entwicklungsstände (`edge`, `sha-…`) sind **nicht signiert**; nutze für den Betrieb feste Versionen.

## Container

- Der **Server-Container läuft nicht als root** (Benutzer `node`); `web` ist das unveränderte Caddy-Image.
- Wer das Netz sauber trennen will, kann die Container so beschränken, dass sie zwar ins Internet (Suchmodell, Kalender-Feeds), aber **nicht in dein Heimnetz** kommen. Das ist optional und hängt von deiner Firewall ab (z. B. Regeln in der `DOCKER-USER`-Kette von `iptables`).
- Das Studio zur Datenbank gibt es nur in der Entwicklung (`docker-compose.dev.yml`); betreibe es nicht öffentlich.

## Wenn etwas passiert

Vermutest du einen Einbruch: Container stoppen, `JWT_SECRET`/`JWT_KEYS`/`APP_SECRET` und Passwörter erneuern, Nutzer zum erneuten Anmelden bitten. Eine **Sicherheitslücke im Projekt** meldest du privat, siehe [SECURITY.md](https://github.com/erik1g/study-manager/blob/main/SECURITY.md).
