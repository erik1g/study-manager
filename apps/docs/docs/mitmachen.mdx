# Mitmachen

## Wo was liegt

```
packages/ui/
  src/tokens.ts          ← alle Farben, Größen, Bewegungen
  src/styles/tokens.css  ← daraus erzeugt (pnpm --filter @study/ui tokens)
  src/styles/*.css       ← das Aussehen der Bausteine, alles mit ui- davor
  src/components/*.tsx   ← die Bausteine
  test/                  ← Tests (Kontraste, Aufbau, Barrierefreiheit)
apps/docs/
  docs/                  ← diese Seiten (MDX)
  src/components/        ← Vorschau, ✓/✗, Props-Tabelle
```

## Einen Baustein anlegen

1. **Gibt es ihn schon?** Oft reicht eine Variante oder eine Prop an einem bestehenden.
2. Komponente in `packages/ui/src/components/<Name>.tsx`. Jede Prop bekommt einen Kommentar – daraus wird die Props-Tabelle.
3. CSS in die passende Datei unter `src/styles/`, Klassen mit `ui-`, Farben nur über Tokens.
4. In `src/index.ts` exportieren.
5. Ein Test in `test/`, vor allem für Rollen, Namen und Zustände.
6. Eine Seite in `apps/docs/docs/bausteine/<gruppe>/` mit den Abschnitten **Beispiel · Varianten und Zustände · Wann benutzen · Props · Barrierefreiheit**.
7. `pnpm --filter @study/ui test` und `pnpm --filter @study/docs build`.

## Eine Farbe ändern

Nur in `src/tokens.ts`, dann `pnpm --filter @study/ui tokens`. Der Test prüft danach, dass `tokens.css` passt und jeder Text mindestens 4,5 : 1 Kontrast hat.

## Die UI-Prüfung

Damit die App einheitlich bleibt, schlägt die CI fehl, wenn in `apps/web`

- ein `<button>`, `<input>`, `<select>` oder `<textarea>` direkt steht,
- eine Farbe als Hex-, `rgb()`- oder `hsl()`-Wert vorkommt (außer in den Tokens),
- eine alte Klasse wie `button`, `icon-button` oder `popover` benutzt wird.

Die Prüfung steckt im Build der App (`pnpm --filter @study/web build`) und lässt sich auch allein starten: `pnpm --filter @study/web check:ui`. Ausnahmen gibt es nur mit `ui-allow: <Grund>` in einem Kommentar in der Zeile davor – zum Beispiel für das Weiß einer PDF-Seite, die in beiden Darstellungen Papier ist.

## Prüfungen vor dem Merge

Die CI führt bei jedem Pull Request die UI-Prüfung, die Typprüfung, die Tests und den Build aus. Die Playwright-Tests (Chromium, WebKit und iPhone, Abläufe, Rollen, Barrierefreiheit mit axe und die Bildvergleiche in Hell und Dunkel, `apps/e2e`) laufen gegen den **Test-Stack mit den gebauten Images** – bei jedem Pull Request nach `dev` oder `main` (Pflicht) und bei anderen Pull Requests mit dem Label `e2e`. Mehr dazu unter [Tests](/entwickler/tests) und [Releases](/entwickler/releases).

Gewollte Änderungen am Aussehen übernimmt `./infra/test/stack.sh e2e --update-snapshots`; die neuen Bilder unter `apps/e2e/tests/__screenshots__/` gehören mit in den Commit.
